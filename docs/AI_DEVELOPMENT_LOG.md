A record of how AI assistance was used while building Smart Writing Pad, what it decided, what
it got wrong, and how the result was verified.

## 1. Summary of the work

The application was implemented in a single AI-assisted session working from a written project
brief. The assistant inspected an empty working directory, scaffolded the project, implemented
the library, components and screens, wrote the test suites, ran them, fixed the defects they
exposed, captured the screenshots from the running application, and wrote this documentation set.

Approximate scope of the result:

| | Count |
| --- | --- |
| Source files (`src/`) | 28 |
| Unit tests | 145 across 8 files |
| End-to-end tests | 29 scenarios run at 2 viewport sizes = 58 |
| Characters with hand-authored stroke data | 62 (A–Z, a–z, 0–9) |
| Screens | 9 |

## 2. Technical decisions, and who made them

The brief specified a preferred stack (React, TypeScript, Vite, Tailwind, Canvas, Pointer Events,
local storage, Vitest, Playwright). That stack was adopted. The decisions *within* it were made
during implementation and are recorded here because they are the ones worth being able to defend:

| Decision | Reasoning |
| --- | --- |
| **Hand-author a single-line stroke font rather than use a font file or SVG outlines** | Outlines carry no stroke order. Ordered polylines produce the trace path, the start dot, the direction arrow and the stroke count from one source, and can be compared directly against the child's ink. This is the decision the whole tracing feature rests on. |
| **Report two geometric measures, not one "accuracy" score** | The brief explicitly warned against fake handwriting recognition. Coverage and on-guide are each definable in a sentence and testable; a single blended score would not be. Requiring both defeats the obvious ways to cheat. |
| **Resample both ink and guide before measuring** | Without it the score depends on drawing speed, because a slow drag produces many more pointer samples than a fast one. |
| **Store strokes in sheet units rather than pixels** | Keeps drawings correct across resizes and devices, and lets the scorer compare ink to the guide with no conversion. |
| **Guide in SVG under a transparent canvas** | Keeps the guide crisp at any size, un-erasable, and separable from the ink for scoring and export. |
| **Snapshot-based undo** | Simpler and more robust than inverse operations, at negligible cost for this data size. |
| **Hash routing** | The static build has to work on Vercel, Netlify, GitHub Pages and `file://` without server rewrites. |
| **An eraser that removes whole strokes** | Keeps erasing undoable and keeps exported PNGs clean, unlike painting white. |
| **`null` rather than `0` for unmeasured attempts** | "Not measured" and "scored zero" are different statements, and the dashboards must not conflate them. |
| **No backend** | Nothing in the MVP requires one, and adding one would mean storing children's data. |

## 3. Tests performed

All tests were executed, not merely written. Commands and outcomes:

```
npx tsc -b --noEmit          → no errors
npm test                     → 8 files, 145 tests, all passing
npx playwright test          → 58 tests (desktop + mobile), all passing
npm run build                → succeeded; 336 kB JS (104 kB gzipped), 25 kB CSS (6 kB gzipped)
npm run screenshots          → 13 screen captures + 26 glyph close-ups from the running app
```

The end-to-end tests drive a real Chromium browser. They read the guide paths out of the rendered
SVG and trace them with the mouse, so they follow the same path a child would and no layout maths
is duplicated in the test code.

Screenshots in `docs/screenshots/` were produced by driving the running application; none were
drawn or mocked up, and the data visible in the progress and review screenshots was generated by
the test script actually performing those exercises.

## 4. Defects found and fixed during the session

Each of these was found by running the code, not by inspection:

1. **Four glyphs overshot their writing lines.** A unit test comparing every character's bounds
   against the baseline and descender caught `g`, `j`, `s` and `u` hanging too low. The arc
   centres and radii were corrected.
2. **Stroke-order markers collided.** On letters whose strokes share a start point — A's two
   diagonals, g's bowl and stem, 5's stem and hat — marker "1" was drawn completely underneath
   marker "2", making the stroke order unreadable. This was found by looking at the captured
   screenshots. Fixed by offsetting each marker backwards along its own stroke direction and
   running a relaxation pass that separates any remaining overlapping pair; a unit test now
   asserts a minimum separation across all 62 characters.
3. **The writing sheet rendered taller than the viewport.** At desktop width a single-letter
   sheet was roughly 730 px tall, so clicking any control scrolled the pad off-screen. This
   surfaced while debugging an end-to-end failure and was initially mistaken for a test problem;
   investigating the actual coordinates showed it was a real layout defect. Sheet height is now
   capped at 58vh.
4. **The review table was unusable on a phone.** Nine columns at 393 px put the "needs practice"
   checkbox out of reach. Secondary columns are now hidden below the `md` breakpoint; the full
   detail remains in the CSV export.
5. **A sticky page header swallowed ink.** The header was pinned to the top of the viewport, so
   whenever the writing sheet scrolled underneath it, pointer events for strokes drawn across
   that band hit the header instead of the canvas and the ink simply never appeared. It showed
   up as a tracing scoring 51% coverage but 100% on-guide — every mark landed on the letter, yet
   half the letter had no ink — which is what made it clear the input was being lost rather than
   misplaced. The header is no longer sticky, and an end-to-end test now traces a letter with the
   sheet deliberately scrolled flush to the top of the viewport.
6. **Scoring depended on drawing speed** before resampling was added.
7. **`5` was drawn right-to-left.** The first stroke ran from the right end of the top bar,
   contradicting normal teaching. Reordered to stem, bowl, then the hat left-to-right.
8. **A test asserted something false.** An early scoring test assumed tracing "stroke 1" of `L`
   would cover only part of the letter — but `L` is a single stroke, so coverage was correctly
   100%. The test was wrong, not the code; it was rewritten against `T`, which genuinely has two
   strokes.

## 5. Limitations of this process

- **AI assistance does not substitute for understanding the code.** Anyone presenting this
  project should be able to explain any file they are asked about. The `DEMO_GUIDE.md` viva
  questions are a reasonable self-test.
- **No evaluation with children was performed**, by the assistant or anyone else. No claim about
  educational effectiveness appears anywhere in the project, and none should be added.
- **Testing covered Chromium only**, at two viewport sizes. Safari and Firefox support every API
  used and are expected to work, but this has not been verified.
- **The letterforms are one person's judgement about teaching order**, informed by common
  print-handwriting conventions rather than by a specific published curriculum. A school
  following a particular scheme (for example a specific national handwriting policy) may order
  or shape some letters differently.
- **The accessibility work follows established practice** — semantic landmarks, labelled
  controls, live regions, focus visibility, reduced-motion support, a high-contrast theme — but
  the application has not been tested with a screen reader by a real user of one, and no formal
  WCAG audit was carried out.
- **No hardware was built.** `HARDWARE_EXTENSION.md` is a design proposal and says so.
